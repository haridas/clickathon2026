01

The identity everything else decomposes

Revenue accrues only on impressions, so this holds exactly — not approximately — for any window, any segment:

Revenue  =  Requests × Fill rate × Render rate × eCPM / 1000

Fill rate is fills / requests, render rate is impressions / fills, eCPM is revenue per thousand impressions. When revenue moves, it moved because exactly one or more of these four factors moved — the question the whole pipeline exists to answer is which one, in which segment, and is it real or an artifact of how the traffic mix shifted underneath it.

The submission below is organized the way the pipeline itself is organized: ingest, decompose, detect, explain. Section 2 is the architecture. Section 4 is the four algorithms that do the actual reasoning. Section 6 is what they found — 2 incidents in the sealed unseen dataset the challenge released, plus 5 more the same detector recovers when pointed at the full 40-day history, including one nobody had found before.

02

Pipeline architecture

Four stages. Data lands once, in the raw fact table; everything downstream is a materialized view that fires on that same insert — there is no scheduler, no cron, no batch window. An alert can exist within the same transaction as the event that caused it.

03

Why each table exists

Nothing here is a generic star schema. Every table is shaped by a specific decision about what it needs to answer quickly — the catalog below is also the argument for why it's structured that way.

ad_events
10.5M rows · MergeTree
The single source of truth. Everything else is derived from it and can be rebuilt from it. Ordered by (toStartOfHour(event_time), app_id) so hour-range scans are sequential reads, not random I/O.
dict_apps / dict_geo / dict_adv
COMPLEX_KEY_HASHED dictionaries
Every downstream rollup needs a dimension label for every event. A dictionary lookup is O(1) in memory; a JOIN against the dimension table re-plans per query. At this event volume the difference is the gap between a materialized view keeping up with the insert stream and falling behind it.
rollup_totals_1m
57,600 rows · SummingMergeTree
Dimension-free, minute grain. This is what v_factors_1h/1d and the LMDI attribution read — the four global factors don't need a single dimension join, so they shouldn't pay for one.
rollup_marginal_1h
61,440 rows · SummingMergeTree
The drill-down table, and the one deliberate architecture choice worth calling out: it's one row per (dimension, value, hour), built with ARRAY JOIN over a literal array of 9 dimension tuples — not a cube of all dimension combinations. Cost scales with hours × Σ(cardinality), independent of event volume. A full cube over these 9 dimensions would be 29 combinations; this is 9. The existing full cube in this dataset (ad_events_hourly) is 7.9M rows for 9M facts — barely a reduction. This table is 61,440 rows for the same facts, a 167× reduction, because a drill-down only ever needs "what did country=US look like," never "what did country=US ∧ os=iOS17.5 ∧ format=video look like" until a scan has already narrowed to that cross — at which point rollup_os_country_1h exists for exactly that.
rollup_os_country_1h
122,863 rows · SummingMergeTree
The one 2-way cross kept pre-built, because OS × geography is where interaction faults actually live in ad delivery (a specific SDK build on a specific carrier's network). The Jun 28–30 incident below is invisible at full severity without it — the marginal os_version scan alone reads a diluted −12%; crossed against country it's −52%, region-locked to four countries.
v_pricebook_jun / v_fillbook_jun
views over ad_events, June weekdays only
The two baselines every alert is scored against. Not simple period averages — eCPM is keyed to (country × ad_format) and fill/render is keyed to (publisher_tier × ad_format), because those are the actual drivers of each metric, discovered empirically (Section 5). Built as the median across days, not sum/sum, so a planted incident inside the training window can't drag down its own detection threshold.
fill_expected_1d / ecpm_expected_1d
2,120 / 2,520 rows · SummingMergeTree
Per-event expected value, computed once and pre-aggregated to (day, dimension, value) for every one of the 9 dimensions simultaneously. This is what turns "compare against a baseline" from an O(dimensions) re-scan into a single table scan.
alerts_unseen / v_incidents_full
277 raw rows → 18 incident rows
The output layer. alerts_unseen is every segment/day/metric combination that breached threshold — intentionally noisy, so nothing is hidden. v_incidents_full collapses that into one row per real root cause by ranking |z| within each (day, metric) group, reporting everything else as bleed-through rather than a separate incident. See Section 4.3.
04

The four algorithms

4.1 — LMDI factor attribution

For a multiplicative identity, weighting each factor's log-change by L = Δrevenue / ln(rev₁/rev₀) makes the four contributions sum to the revenue delta exactly, with zero residual:

contribution(factor)  =  L × ln(factor₁ / factor₀)

Naive alternatives — hold-one-factor-constant, first-difference — leave an unexplained interaction term. LMDI doesn't: on every incident day below, the four contributions sum to the observed delta to within $0.004. That's not an approximation error rounding away; it's the identity, verified.

4.2 — Rate vs. mix, inside a segment

A segment's contribution to a metric change splits into two exact, additive terms:

rate effect  =  (w₀+w₁)/2 × (m₁-m₀)   // the segment itself changed
mix effect  =  (m₀+m₁)/2 × (w₁-w₀)   // traffic shifted between segments

This is the difference between "a country's fill rate collapsed" and "traffic shifted toward a country that always had lower fill" — two completely different fixes, indistinguishable by looking at the raw number alone. Every incident below reports both; in six of seven the mix effect is ~0 and the rate effect carries the entire move — confirmation that what's being measured is a real fault, not a reshuffle.

4.3 — Concentration ranking & root-cause collapse

For a metric move, rca_scan ranks all 9 dimensions by concentration — the dispersion of per-segment change relative to the overall move:

concentrationreading
≈ 0the move is uniform across every segment — global to that dimension, not a segment fault. Stop looking there.
> 2one segment owns the move. That's the root cause.
two dimensions both > 2an interaction. Cross them — this is exactly what happened with iOS 18.1 × APAC below.

Once a root cause is found, the same 19%-share segment dropping 40% must move every dimension that overlaps it by up to ~7.7% — that's arithmetic, not 25 independent incidents. v_incidents_full ranks every alert within its (day, metric) group by |z| and keeps only the top row as the root cause, reporting the rest as bleed_through_alerts — a count that's a consistency check on the diagnosis, not noise to suppress.

4.4 — Two noise models, matched to what's actually being counted

Fill rate and render rate are proportions of a known trial count — this many requests, this many filled. They get a binomial standard error, inflated by an overdispersion factor φ=1.6 so real-world clustering (one app having a bad minute) doesn't produce false positives from a model that assumes independence:

z  =  (p_observed − p_baseline) / (φ × √(p·(1−p)/n))

eCPM has no trial count — it's a continuous ratio — so it's scored on relative deviation against a 0.5% noise floor, set at 20× the ±0.025pp residual measured out-of-sample on 7 held-out days. And requests, a raw count with real weekday/weekend structure, uses median + MAD against the same-day-type history rather than mean + stddev, so a past incident inside the baseline window can't inflate the very threshold meant to catch the next one — the exact bug the first version of this pipeline had, documented in Section 5.

05

The trap: dimension tables that were quietly regenerated

The sealed unseen dataset ships three new dimension CSVs — same app_id/geo_device_id/advertiser_id keys, but every attribute value regenerated: 82% of apps changed category, 92% of geo profiles changed country, 85% of advertisers changed vertical. This is the part of the submission where the pipeline had to prove it generalizes, not just replay a rehearsed answer.

The wrong move, either direction

The obvious read is "restate history through the new labels and compare." The other obvious read is "the old rollups are still valid as-is." Both are wrong — and each is wrong for a different half of the metrics, which is what makes this trap effective: whichever one you pick, half your numbers look perfectly reasonable.

Measured: eCPM, country dimension
1.7% error using old labels as-is. 67–73% error restated through new labels. Price is a property of the label — a country's market rate carries across a relabeling; a device's price does not follow it.
Measured: segment traffic share
8–24pp error using old labels as-is. ≤1.2pp error restated through new labels. Volume is a property of the device ID — a device keeps its traffic when relabeled; it does not keep its old country's share.

Concretely: under old labels, country=ID carried 6.98% of requests; under new labels, 17.46%. Naively read, that's a massive traffic shift toward Indonesia. It's entirely relabeling — the restated old-period figure is 17.47%, matching to a hundredth of a point. Meanwhile per-country eCPM barely moved across the boundary (US $3.633 → $3.559) — visible only if you don't restate. A detector that skipped this distinction would have raised four false P1 eCPM alerts on completely clean days, at almost 2× the actual incidents' severity.

The fix: never baseline the segment, baseline the driver. fill_rate and render_rate are keyed to publisher_tier × ad_format (0.81% error vs. 14.26% for the naive tier-only version); eCPM is keyed to country × ad_format. Expected value for any segment on any day becomes Σ observed_events × driver_rate — the mix cancels by construction, so a segment only flags when its own rate moved, which is what an incident actually is.

A second version of the same trap, caught mid-submission

Making the pipeline self-contained meant loading the main dataset's 9M events into the same table as the unseen slice, with both dimension snapshots live side by side. The first attempt at rescoring hard-coded the current (unseen) dictionary for every lookup — including main-dataset events. Result: country=AE came back at z = +327, a +162% eCPM "incident," on 30 of 35 June days. The fix is a per-event dictionary switch — if(event_time < boundary, dict_v1, dict_current) — applied at every lookup, not assumed constant for a backfill. This is the same trap in a different location: it isn't enough to know the rule once, the rule has to be re-applied correctly every time two label epochs coexist in one table.

Why request volume needed a 5th detector
Fill and eCPM detectors score rates, which are blind to a uniform drop in the request stream itself — a pipe flowing at half rate still shows a normal fill rate. v_request_alerts closes the gap with median+MAD on daily request counts. It fires exactly once, on Jun 21. A retention check confirms every one of the 9 dimensions drops 46.6–50.9% — uniform, so it's an ingestion outage, not a demand shock.
Why iOS 18.1 needed the 2-way cross
The single-dimension scan flags os_version=iOS 18.1 at a diluted −12%. Crossed against rollup_os_country_1h, the real shape is iOS 18.1 and four APAC countries together at −52%, with iOS 18.1 everywhere else within 1% of normal. A real-but-weak single-dimension hit is the signature of an interaction — the fix is to cross it, not trust the marginal number.
Jun 16–18 — a genuine new finding, not a rehearsed one
This surfaced only during this submission's full-window rescore and wasn't in the original analysis. It first looked like bleed-through from the adjacent Jun 19–22 finance-eCPM incident, but the two don't overlap in time (finance eCPM is flat through Jun 18) or mechanism (finance is only 18% of interstitial volume, not concentrated there). Crossing ad_format=interstitial against country shows the real shape: FR/UK/ES/DE drop ~19.7% for exactly three days while every other country sits flat at +1%.
